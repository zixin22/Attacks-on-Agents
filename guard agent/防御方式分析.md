## 一、GuardAgent 防御机制详解

### 1.1 核心架构

GuardAgent 是一个基于 **AutoGen** 框架的守护代理系统，采用 **"任务分解 → 代码生成 → 动态执行"** 的三阶段防御机制。

```
┌─────────────────────────────────────────────────────────────┐
│                    GuardAgent 工作流程                       │
└─────────────────────────────────────────────────────────────┘

输入: 用户请求 + 代理规格 + 代理输入/输出
  │
  ├─→ [阶段1] 任务分解 (Task Decomposition)
  │     └─→ LLM分析并生成子任务列表
  │
  ├─→ [阶段2] 示例检索 (Example Retrieval)
  │     └─→ 基于Levenshtein距离检索相似历史案例
  │
  ├─→ [阶段3] 代码生成 (Code Generation)
  │     └─→ Few-shot学习生成Python检查代码
  │
  ├─→ [阶段4] 代码执行 (Code Execution)
  │     └─→ 执行生成的代码，调用CheckAccess/CheckRule
  │
  └─→ [阶段5] 结果返回 (Result Return)
        └─→ 返回检查结果（label, inaccessible_db, guardrailed_answer）
```

#### **2. 示例检索模块 (`retrieve_examples`)**

**功能**：从长期记忆中检索最相似的示例

**实现方式**：
- 使用 **Levenshtein距离** 计算相似度
- 距离公式：`distance(input1, input2) + distance(output1, output2)`
- 选择距离最小的前 N 个示例（N = num_shots）

**代码位置**：`guardagent.py:85-101`

```python
def retrieve_examples(self, agent_input, agent_output):
    levenshtein_dist = {}
    for i in range(len(self.memory)):
        mem_input = self.memory[i]["agent input"]
        mem_output = self.memory[i]["agent output"]
        # 计算编辑距离
        levenshtein_dist[i] = Levenshtein.distance(agent_input, mem_input) + \
                              Levenshtein.distance(agent_output, mem_output)
    # 选择最相似的N个示例
    selected_indexes = [levenshtein_dist[i][0] 
                        for i in range(min(self.num_shots, len(levenshtein_dist)))]
    return examples
```

**优势**：
- ✅ 自动学习历史成功案例
- ✅ 支持Few-shot学习（1-shot, 2-shot, 3-shot）
- ✅ 无需手动标注训练数据

**劣势**：
- ❌ 依赖历史数据质量
- ❌ Levenshtein距离对长文本计算开销大

#### **3. 代码生成模块 (`generate_init_message`)**

**功能**：基于Few-shot示例生成Python检查代码

**实现方式**：
- 使用 `GuardAgent_Message_Prompt` 模板
- 输入：检索的示例 + 当前输入/输出 + 子任务
- 输出：Python代码字符串

**代码位置**：`guardagent.py:103-127`

**生成的代码特点**：
- 调用预定义函数：`CheckAccess()` 和 `CheckRule()`
- 设置全局变量：`access_denied`, `inaccessible_database`, `guardrailed_answer`
- 必须包含所有必需的变量

#### **4. 代码执行模块 (`execute_function`)**

**功能**：执行生成的Python代码并捕获结果

**实现方式**：
- 使用 `exec()` 执行代码
- 在隔离的全局变量空间中运行
- 捕获执行结果和错误信息

**代码位置**：`guardagent.py:192-247`

**安全机制**：
- ✅ 在隔离环境中执行
- ✅ 捕获所有异常
- ✅ 错误自动诊断和修复

**风险**：
- ⚠️ 动态代码执行存在安全隐患
- ⚠️ 可能执行恶意代码（如果Prompt被注入）

#### **5. 错误调试模块 (`error_debugger`)**

**功能**：当代码执行失败时，自动诊断错误原因

**实现方式**：
- 解析错误类型（SyntaxError, KeyError, TypeError等）
- 调用LLM分析错误原因
- 提供修复建议

**代码位置**：`guardagent.py:158-190`

**错误处理流程**：
```

  ↓
解析错误信息（错误类型、错误行、错误消息）
  ↓
调用LLM诊断（CodeDebugger Prompt）
  ↓

```

### 1.3 核心工具函数

#### **`CheckAccess(DATABASE_ALLOWED, DATABASE_NEEDED)`**

**功能**：检查数据库访问权限

**实现**：`tools.py:1-18`

```python
def check_access(list_of_database: dict, summary_of_database: dict):
    access_denied = False
    inaccessible = {}
    
    # 检查数据库访问权限
    for key, value in summary_of_database.items():
        if key not in list_of_database:
            access_denied = True
            inaccessible[key] = value
        else:
            # 检查列访问权限
            inaccessible_column_temp = list(set(value) - set(list_of_database[key]))
            if len(inaccessible_column_temp) > 0:
                access_denied = True
                inaccessible[key] = inaccessible_column_temp
    
    return access_denied, inaccessible
```

**适用场景**：EhrAgent（医疗数据库访问控制）

#### **`CheckRule(list_of_rules: dict, user_info: dict)`**

**功能**：检查规则违反情况

**实现**：`tools.py:21-42`

```python
def check_rule(list_of_rules: dict, user_info: dict):
    access_denied = False
    inaccessible = {}
    
    for act in list_of_rules.keys():
        info_type = list_of_rules[act]['info']
        info_value = list_of_rules[act]['value']
        info_op = list_of_rules[act]['operator']
        
        actual_value = user_info[info_type]
        # 动态评估条件：actual_value {operator} info_value
        access_denied_ = not eval(f"actual_value {info_op} info_value")
        
        if access_denied_:
            inaccessible[act] = list_of_rules[act]['violation']
    
    return access_denied, inaccessible
```

**适用场景**：SeeAct（Web操作规则检查）

**注意**：使用 `eval()` 存在安全风险，但在这里是受控的（只评估数值比较）

### 1.5 优势与劣势总结

#### ✅ **优势**

1. **高度灵活**
   - 通过Prompt定义规则，无需修改代码
   - 适应不同领域（医疗、Web操作等）

2. **可解释性强**
   - 生成的代码可查看和审计
   - 任务分解过程透明

3. **自学习能力**
   - 长期记忆机制
   - 从成功案例中学习

4. **通用性强**
   - 不局限于特定领域
   - 可适配多种代理类型

#### ❌ **劣势**

1. **执行开销大**
   - 需要多次LLM调用（任务分解 + 代码生成 + 错误调试）
   - 每次检查可能需要3-5次API调用

2. **延迟较高**
   - 多步骤流程导致响应时间长
   - 不适合实时性要求高的场景

3. **代码执行风险**
   - 动态执行生成的代码存在安全隐患
   - 可能被Prompt注入攻击

4. **依赖示例质量**
   - Few-shot示例的质量直接影响效果
   - 需要精心设计示例

5. **调试复杂**
   - 多步骤流程难以定位问题
   - 错误可能出现在任何阶段

## 二、RuleChecker 防御机制详解

### 2.1 核心架构

RuleChecker 采用 **"规则硬编码 → 类别识别 → 批量检查"** 的直接防御机制。

```
┌─────────────────────────────────────────────────────────────┐
│                  RuleChecker 工作流程                        │
└─────────────────────────────────────────────────────────────┘

输入: 用户配置文件 + 指令 + 查询
  │
  ├─→ [步骤1] 提取当前会话指令
  │     └─→ 从"Here is the task."后提取Instruction
  │
  ├─→ [步骤2] 识别产品类别
  │     └─→ 从指令和查询中识别产品类别
  │
  ├─→ [步骤3] 构建检查Prompt
  │     └─→ 包含所有10条规则 + 用户配置 + 购买上下文
  │
  ├─→ [步骤4] 单次LLM调用
  │     └─→ 批量检查所有相关规则
  │
  └─→ [步骤5] 解析结果
        └─→ 返回VALID或VIOLATED:rule1,rule2...
```

### 2.2 规则定义系统

#### **10条业务规则**

RuleChecker 定义了10条明确的业务规则，每条规则包含：

1. **规则名称**：如 `rule1_age_alcohol`
2. **规则描述**：详细的规则说明
3. **触发类别**：触发该规则的产品类别列表
4. **检查字段**：需要检查的用户配置字段

### 2.3 类别触发机制

#### **核心逻辑**

1. **提取当前会话指令**
   - 从 "Here is the task." 后提取
   - 忽略历史记忆示例
   - 只使用当前会话的指令

2. **识别产品类别**
   - 严格基于指令中的显式词汇
   - 不进行推理或猜测
   - 必须与规则中的触发类别明确匹配

3. **规则触发**
   - 只有匹配到产品类别才触发相关规则
   - 如果无法识别类别，返回VALID（不触发任何规则）

**代码位置**：`rule_checker.py:265-308`

### 2.4 LLM批量检查

#### **单次调用设计**

**优势**：
- ✅ 减少API调用次数（只需1次）
- ✅ 降低延迟
- ✅ 降低API成本

**实现方式**：
- 构建包含所有规则的完整Prompt
- LLM一次性分析所有相关规则
- 返回格式：`VALID` 或 `VIOLATED:rule1,rule2,...`

**代码位置**：`rule_checker.py:143-371`

```python
def _check_all_rules_with_llm(self, profile: UserProfile, 
                              instruction: str, query: str) -> List[str]:

    - Instruction: {instruction}

    # 单次LLM调用
    response = self._call_llm(prompt)
```

### 2.6 优势与劣势总结

#### ✅ **优势**

1. **执行效率高**
   - 单次LLM调用完成检查
   - 响应速度快（通常<2秒）

2. **延迟低**
   - 无需多步骤流程
   - 适合实时性要求高的场景

3. **规则明确**
   - 规则硬编码，易于理解和维护
   - 规则变更需要代码修改，但更可控

4. **安全性好**
   - 不执行动态代码
   - 只进行LLM推理，风险低

5. **成本低**
   - 单次API调用
   - 降低API使用成本

#### ❌ **劣势**

1. **灵活性低**
   - 规则硬编码，难以适应新场景
   - 添加新规则需要修改代码

2. **领域特定**
   - 专门针对WebShop电商场景设计
   - 难以跨领域复用

3. **可扩展性差**
   - 规则数量增加时，Prompt会变长
   - 可能超出LLM上下文限制

4. **可解释性中等**
   - LLM推理过程不透明
   - 难以调试为什么某个规则被触发

## 四、替代可行性评估

### 4.1 技术可行性

#### ✅ **技术上可行**

GuardAgent 可以替代 RuleChecker，因为：

1. **功能覆盖**
   - GuardAgent 可以检查任何规则
   - 通过Prompt定义WebShop的10条规则

2. **接口兼容**
   - 可以封装为相同的接口
   - 返回格式可以统一

3. **集成可行**
   - 可以集成到WebShop环境
   - 可以替换现有的RuleChecker调用

### 4.2 性能影响

#### ⚠️ **性能会下降**

如果替代，预期影响：

- **延迟增加**：从1-3秒增加到5-15秒（3-5倍）
- **API成本增加**：从1次调用增加到3-5次调用（3-5倍）
- **资源消耗增加**：需要执行动态代码

### 4.3 功能影响

#### ✅ **功能可能增强**

- **规则灵活性**：更容易添加新规则
- **可解释性**：可以查看生成的代码

## 六、总结与建议

### 6.1 核心结论

1. **GuardAgent可以替代RuleChecker**
   - 技术上完全可行
   - 功能上可能更强大

2. **但替代会带来性能损失**

   - API成本增加3-5倍

3. **替代的价值取决于需求**
   - 如果规则固定：不建议替代
   - 如果规则频繁变化：建议替代
   - 如果需要跨领域复用：建议替代

### 6.2 最终建议

#### **对于WebShop项目**

**不建议完全替代**，原因：
- ✅ WebShop的10条规则相对固定
- ✅ 性能要求高（实时检查）
- ✅ 成本控制重要（大量API调用）

**建议采用混合方案**：
- 固定规则使用RuleChecker（性能优先）
- 新规则或复杂规则使用GuardAgent（灵活性优先）
- 逐步迁移，降低风险
